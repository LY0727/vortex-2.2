## 2 SIMT模型与RISC-V自定义指令扩展

### 2.1 SIMT执行模型与硬件特性分析

在面向图形渲染、高性能计算以及人工智能等领域时，应用程序通常表现出极强的数据并行性（Data Parallelism）。为了高效处理海量数据，传统的 SIMD（单指令多数据流）架构虽然能在单个时钟周期内执行多个相同的数据运算，但由于要求所有数据通道绝对一致，其在处理复杂分支逻辑时显得极为僵硬。为此，现代 GPGPU 广泛采用了 SIMT（单指令多线程，Single Instruction Multiple Threads）计算模型。SIMT 既保留了 SIMD 高效吞吐的硬件优势，又在编程模型上为每个线程提供了相对独立的执行上下文，极大提升了并行编程的灵活性。

#### 2.1.1 数据并行与层次化线程模型

为了将庞大规模的数据并行任务合理且高效地映射到具体的底层硬件上，产业界（如 NVIDIA CUDA、OpenCL）对 SIMT 模型进行了高度抽象，形成了一套**层次化的线程组织模型**。

在此模型中，程序员只需要编写单一标量线程的执行代码（即 Kernel 函数），但在运行时，系统会实例化出成千上万个线程并发执行。以典型结构为例，这些海量的计算任务被抽象划分为了三个层级：

1. **网络/网格（Grid / NDRange）**：代表一次完整的计算内核启动任务。
2. **线程块（Block / Work-group）**：处于网格内部，包含若干协同工作的线程。同一线程块内的线程可以通过屏障（Barrier）进行粗粒度的同步。
3. **线程（Thread / Work-item）**：最基础的执行单元。每个线程拥有独立的程序计数器（PC）逻辑和局部寄存器状态，负责处理被分配到的具体数据元。

这种自顶向下的线程模型不仅契合了数据切分的逻辑，也恰好能完美映射到 GPGPU “芯片 - 流式多处理器 (SM) - 执行通道 (Lane)” 的层次化硬件拓扑中。

#### 2.1.2 面向SIMT的微架构硬件协同特征

为了支撑上述高度并发且允许局部独立控制的层次化线程模型，底层的流式多处理器（SM-Core）在微架构设计上必须具备有别于传统通用处理器（CPU）的一系列核心硬件特性。这些特性也是本论文后续进行 RISC-V 核心微架构设计的基石：

**1. 线程束（Warp）打包与前端共享机制**
在实际硬件调度中，如果为成百上千个线程分别配备独立的取指和译码单元（Fetch & Decode），将造成极其巨大且无谓的面积和功耗浪费。因此，SIMT 硬件在微架构层面将一定数量（如 4、16 或 32）的纯量线程绑定为一个**线程束（Warp / Wavefront）**作为最小调度与拉取单位。同一个 Warp 内的所有线程共享单个程序计数器（PC），共用一套指令提取和译码前端，但在后端的执行流片（Lanes）中各自使用独立的运算器（ALU）和数据通路，从而实现了单指令周期的并行宽幅推力。

**2. 海量并发寄存器堆（Massive Register File）**
SIMT 处理器不仅依靠高计算密度，更依赖**延迟隐藏（Latency Hiding）**技术来规避长周期的流水线停顿（如 Cache Miss 或访存等待）。为了在不同 Warp 之间实现“零时钟周期”的上下文切换，微架构必须为所有被分配到该 Core 的活跃 Warp 提供极其庞大的物理寄存器堆（RF）。当某一个 Warp 因为数据冒险或访存处于挂起（Stall）状态时，硬件调度器可以瞬间将执行权切换给另一个处于就绪态的 Warp，这要求每一个线程的历史寄存器上下文都在 RF 中得以常驻保留，而不需要像 CPU 那样发生昂贵的栈溢写（Spill）操作。

**3. 线程掩码（Thread Masking）与分支栈机制**
SIMT 模型下，尽管同一 Warp 的线程被迫以锁步（Lock-step）的方式提取同一条指令，但由于它们各自处理的数据不同，在遇到依赖数据的条件跳转指令（如 `if-else` 或 `while`）时，不可避免地会遭遇控制流发散（Divergence）问题。此时，硬件引入了**线程掩码（Thread Mask / Tmask）**，用于逐个标记本回合参与有效化执行的线程（Active）和被屏蔽的线程（Inactive）。配合底层的**硬件分支管理栈（如 IPDOM Stack）**，SM-Core 能够自动序列化地处理多条发散路径并在分支合束点实现正确重聚。

**4. 硬件级细粒度调度网络**
面对几十乃至上百个同时进驻流水线的并发 Warp，SM-Core 内部需要包含一个细粒度、低延迟的硬件调度器（Warp Scheduler）。它通过计分板（Scoreboard）等机制时刻监控各 Warp 所属内部线程的指令停顿与资源冒险情况，在每个时钟周期基于就绪状态、优先级与流水线资源余量等条件实时挑出最优 Warp 灌入执行流水线。

综上所述，要在基础的 RISC-V 标量指令集架构上实现拥有并发执行能力的 SM-Core，微架构设计必须深度围绕上述特征进行扩充与适配。传统的 RISC-V 缺乏原生调度与掩码干预能力，这便直接催生了对其进行 GPGPU 专用自定义指令扩展的迫切需求。

### 2.2 RISCV指令集

### 2.3 自定义RISCV扩展指令

传统的RISC-V 指令集由于主要针对标量（Scalar）处理器设计，缺乏对多线程束协同调度、掩码控制（Masking）以及流水分化控制的原生支持。为了在基础的 RV32IM 核之上建立 SIMT (Single Instruction Multiple Threads) 计算模型，本设计在 RISC-V 预留的自定义指令空间中，设计并引入了一组 GPGPU 专用的线程与分支控制扩展指令。

#### 2.3.1 指令定义与功能

为了满足SIMT 架构中动态控制流操作和并发管理的需求，本设计定义了 6 条线程控制指令。这组指令深度耦合了底层的线程束调度器、分化处理栈以及Scoreboard 资源追踪机制。各指令的具体定义如下（见表2-1）：

| 指令定义             | 指令描述               |
| -------------------- | ---------------------- |
| wspawn #warps, %PC   | 线程束激活指令         |
| tmc #threads         | 线程掩码配置指令       |
| #addr ← split #pred | 分支发散指令           |
| join #addr           | 分支合并指令           |
| pred #pred, #mask    | 谓词预测指令           |
| bar #id, #warps      | 线程数同步（屏障）指令 |

Wspawn指令：该指令唤醒并调度新的线程束，用于内核（Kernel）计算任务的并行初始化。硬件中以#warps（rs1）为总数配置线程束的激活状态（除线程束0自身外），并读取%PC（rs2）的值作为新生线程束的初态指令计数器值。

Tmc指令：动态设置当前执行线程束的活跃线程掩码。硬件中将当前线程束的线程掩码寄存器直接更新为#threads（rs1）的值。被屏蔽的 Lane 在后端流水线中不再进行发射、执行、写回等操作，实现基础的谓词控制。

Split指令：评估条件发散并压入未跳转路径状态。基于#pred（rs1）中的谓词数据和指令隐含的极性位，计算分支的Taken和Not-Taken掩码，将待延后执行的分支状态压入 IPDOM 硬件分化栈，并将栈顶指针写入目标寄存器#addr（rd）。

Join指令：从硬件分化栈中恢复上下文，实现控制流的重收敛。以#addr（rs1）为输入指针，直接寻址IPDOM栈并弹出挂起的Not-Taken掩码与PC值，将其重装载到线程束状态中，从而执行延后执行的分支，或者是合并所有分支继续执行后续代码。

pred指令：用于循环（While）结构的线程掩码控制。根据#pred（rs1）的谓词结果来设置当前线程束的激活掩码，实现while结构下的线程控制；当#pred（rs1）的值为全0时，说明每个线程都不需要执行while循环内的代码了，此时线程掩码设置为#mask(rs2)的值，继续执行后续代码。

Bar指令：实现线程束级别的并发同步，保障多线程执行的时序一致性。该指令流经执行流片后会向Schedule 级发送“挂起”标识，硬件将监测同一#id（rs1）（屏障ID）下的线程束数是否累计达到 #warps（rs2）（该屏障下的线程束数量）。若条件满足，则统一解除相关线程束的阻塞状态；否则提前到达了的线程束将被堵塞，等待其它线程束的完成。

自定义的6条扩展指令中，Wspawn指令和Tmc指令实现了基本的线程束模型，在此基础上，硬件可以实现以线程束粒度进行管理、调度、取值、译码，同一线程束内的所有线程共用一套流水前端硬件，即SI模型的概念；同时又可以实现同一线程束下多个硬件线程的并行发射、执行、提交，多个线程虽然执行相同指令，但各自维护独立的PC、寄存器文件和后端流水硬件，可单独控制是否实际执行当前指令，即MT模型的概念。二者结合即可实现SIMT硬件的基本框架。Split指令和Join指令针对SIMT模型下的if-else分支类型的控制流发散场景，实现分批执行的控制流支持；Pred则针对控制流相对简单的while循环类型的控制流场景，通过谓词预测简化控制。程序控制流发散的处理是流式多处理器设计的核心，在下文中详细介绍。Bar指令针对多线程束之间的同步场景需求，设计简洁有效，也适于硬件实现。

#### 2.3.2 指令编码

RISC-V ISA在设计之初即考虑了特定领域的架构创新对自定义扩展指令的需求，在指令集规范中预定义了 custom-0、custom-1、custom-2 和 custom-3 四块自定义编码区间，为微架构层面的硬件加速或专用机制提供了标准化“土壤”。

为尽量减少对前端译码器（Decoder）面积的过度消耗，同时兼顾指令扩展的便利性，本设计的微架构共用 custom-0 空间（操作码 Opcode = 0x0B，即 7'b0001011）来映射所有的 SIMT 扩展指令。所有新增的自定义控制扩展指令均复用了标准的 R-Type 格式字段解析层块，保持 funct7 通用标识位固定（为 7'h00），并单纯依靠 3-bit 的 funct3 编码位来实现子扩展指令操作的具体身份区分。这种设计规避了重新引入新的字段解析逻辑电路，确保核心流水线在译码阶段的“干净”与延迟性能。

由于这类指令不存在真正的“计算”或“访存”，其参数大部分为控制状态字或指针，故对传统的寄存器下标字段进行了复用设计。其硬件操作编码分配如表 2-x 所示：

| 指令 (Instr)         | `func7` [31:25] |               `rs2` [24:20]               |   `rs1` [19:15]   | `func3` [14:12] |                `rd` [11:7]                | Opcdoe [6:0] |
| :------------------- | :---------------: | :------------------------------------------: | :-----------------: | :---------------: | :-----------------------------------------: | :----------: |
| **`tmc`**    |    `0000000`    |                      -                      |    *Mask 数据*    |      `000`      |                      -                      | `0001011` |
| **`wspawn`** |    `0000000`    |               *PC 起始地址*               | *发起的 Warp 数* |      `001`      |                      -                      | `0001011` |

如表 2-y 所示，在处理带条件状态判断的分发指令 split 以及谓词评估指令 pred 时，指令编码在原应该被解析为寄存器下标 rs2 的第 20 位（或 rd 的第 7 位）的比特向量上，巧妙地重载映射了一个布尔变量特征域 —— is_neg（运算条件极性特征位）。

这一软硬件微结构特性的加入是为了配合复杂上层程序编译控制流。在 GPGPU 的通用 C/C++ 程序抽象语法树（AST）编译执行时，源程序产生的分支逻辑表达式可能会被评估为 "真 (True, >0)" 条件或者 "伪 (False, ==0)" 条件。例如 if(a > b) 或 if(!(a == b)) 这种互为逻辑镜像的代码，其基础评估谓词的结果状态（存于通用寄存器）的绝对值可能是颠倒对应的。

针对上述编程模型特征与系统评估需求的匹配差问题，若依靠显式的指令级取反操作不仅将拉长流水线的执行周期耗时，增加寄存器写回的 WAW 及 RAW 风险等待。因此设计在底层硬件中植入了极权比照逻辑：通过解码引入 is_neg 掩码重定向位，并在调度控制（Warp Control / WCTL Unit）的后传网络端注入一阶轻量化组合逻辑，用于在分支收敛（Taken 判断）前实时反转当前的 Predicate 通道状态流以匹配发散需求。

从体系结构的开放层面而言，这种以比特域直接内嵌指令属性的优化手段减轻了分支调度的硬件复杂包袱，不过代价是将复杂性向编译器前端传递了。在更为完备的软件编译器重构支持下（如配合定制化的 LLVM 后端或中间代码层重写），编译器理应在翻译 AST 层面的抽象语法时主动计算判断条件的正交属性，通过自动下发置位 is_neg 标志生成相应的指令从而保证程序编译下发的黑盒正确性与鲁棒性，而不再依赖人工编写内联汇编汇入冗余极性。

### 2.4  控制流发散处理机制

在 SIMT（单指令多线程）执行模型中，同一线程束（Warp）内的所有子线程默认在同一个程序计数器（PC）下彼此同步地执行相同指令。然而，当程序遭遇像 if-else 或 while 等数据依赖的控制流分支时，不同线程对分支条件的评估结果（即谓词响应 Predicates）可能产生分歧，导致原本并行的线程需要走向并执行不同的指令路径。这种现象被称为“控制流发散”（Control Flow Divergence）。为了在不打破物理硬件锁步（Lock-step）执行约束的前提下兼顾所有路径的处理，硬件层必须提供一套高效的方法来序列化执行这些发散的分支，并在逻辑汇合点恢复并行性能。

#### 2.4.1 if-else分支控制流发散机制

`if-else` 结构是最典型的前向非重叠发散结构。在处理这类发散时，必须保证相互排斥的两条路径能够在硬件流水线中分时执行，同时还要记录并存储那些处于“等待状态”的线程上下文。本设计中，该机制的核心依赖于**立即后继支配树堆栈（Immediate Post-Dominator Stack, IPDOM）**以及前述的 `split` 和 `join` 扩展微指令的支持。

**1) 程序特征与指令插入**
典型的 `if-else` 程序存在明显的分叉与重聚特征。当编译器针对 SIMT 架构进行目标代码生成时，会在原始的条件判断处将其映射为自定义的 `split` 指令，并在各执行路径的重聚点插入 `join` 汇合指令。其高级语言到底层自定义指令的映射范例如下所示：

```c
// 标准高级语言模型：
if (cond) {
    // THEN 路径计算
} else {
    // ELSE 路径计算
}

// SIMT扩展指令映射逻辑：
int sp = split(cond);     // 评估分支条件，记录分离点
if (cond) {
    // THEN 路径指令
} else {
    // ELSE 路径指令
}
join(sp);                 // 利用栈指针 sp 进行路径重聚
```

**2) 分发与汇合（split-ipdom-join）的硬件映射逻辑**

* **IPDOM 栈的功能：** 它是微架构调度模块内嵌的一块硬件 LIFO（后进先出）小存储区，用于在分化发生时，锁存尚未被执行的另一分支（非首选分支）的“断点信息”。这个信息严格包含了：**未跳转目标指令的起始地址（Target PC）** 以及  **响应该路径的待激活线程掩码（Pending Tmask）** 。
* **`split` 指令：** 当进入分化点时被调用。其在内部不仅从工作寄存器内读入分支约束谓词计算分歧掩码，还将掩码和另一条路径的初始PC直接推送（Push）到本 Warp 所隶属的 IPDOM 栈中暂存。
* **`join` 指令：** 被调用于分支运行区块结束的尾部。作用是通知控制流栈指针回退，自动从 IPDOM 栈弹出（Pop）出上一层存储的挂起状态，强制 Warp 更新执行状态以完成所有遗留分支的回收。

**3) 硬件执行时空特性分析**
结合图 2-x 进行时序与状态分析：当执行单元评估到分歧时，`split` 指令会统计 `Taken` (跳转) 以及 `Not-Taken` (未跳转) 两种条件下的有效线程数（Pop-Count）。出于系统指令带宽的吞吐量考量，调度器通常倾向于让活跃线程数较多的分支优先进入前台首发执行（即设置当前运行 Tmask 为多数派），而将线程数处于劣势的较小分支状态信息 `{Next_PC, Minor_Tmask}` 压入 IPDOM 序列栈中。

首发进入的如 `if` 逻辑块在执行自身指令时，那些本应进入 `else` 路径的少数派线程会被当前掩码自动“遮蔽”（Masked-out），既不修改寄存器也不产生有效访存请求。当 `if` 区块末尾触及 `join` 指令，由于硬件识别到当前层次还留存有未处理事务，IPDOM 触发弹栈（Pop），硬件自动重载 `else` 块的目标地址作为最新的 PC 进入取指，并将原先存备的少数派 Tmask 载入当前执行活跃寄存器内完成 `else` 指令的执行。在两个分支均执行终结后，最后一次 `join` 的出栈将使系统的 PC 收敛到最终的支配块结点，同时恢复到进入分叉前的完整 Tmask，完美达成所有线程路径的平行化收回归一。

#### 2.4.2 While循环控制流发散机制

有别于结构呈现两分支开叉的 if-else，while 循环本质上是一种条件驱动的回环结构。这种控制流的发散表现为：随着循环迭代的推进，最初并行执行的一个 Warp 中会有部分线程过早地满足了跳出条件，率先需要停止执行（Break/Exit）；而剩下的线程则必须继续留在环中计算（Continue），直到所有人完成迭代。

在面向循环的分歧处理设计中，针对复杂嵌套与简单循环，硬件提供了两种截然不同的处理机制。这使得编译器可以根据循环体内是否包含嵌套的发散控制流来选择最优的编译映射方案，代码对比如下：

```c
// 标准高级语言循环模型：
while (cond) {
    // 循环体计算
}

// 机制一：基于 IPDOM 栈的 split-join 实现（适用于含有复杂嵌套分支的循环）
int sp;
l_loop:
    sp = split(cond);
    if (cond) {
        // 循环体计算 (内部可能再次改变 cond 的值)
        goto l_loop;
    }
    join(sp);

// 机制二：基于线程掩码动态管理的 pred-tmc 实现（无栈，极轻量级）
int orig_tmask = active_threads();  // 1. 保存进入循环前的活跃线程掩码状态
l_loop:
    pred(cond, orig_tmask);         // 2. 结合条件更新掩码：当前TMC = orig & (满足cond的线程)
    if (active_threads() != 0) {    // 3. 如果Warp中还有线程满足条件，则全Warp继续循环
        // 循环体计算
        goto l_loop;                // 4. 跳转回循环开头重新计算预测
    }
    tmc(orig_tmask);                // 5. 循环结束，恢复初始的线程掩码，确保收敛
```

**循环控制映射与硬件状态演变原理：**

1. **基于硬件栈的 `split-join` 机制**：该机制依赖底层微架构中的 **IPDOM 栈**予以实现。每当跳转至循环头部评测分支时，`split` 指令都会引发硬件动作：向栈中压入一组分支断点数据（包含满足跳出条件的线程掩码与其对应的顺序 PC 以备终局合并）。它完全能够利用硬件栈支持任意深度的复杂多重嵌套，然而代价是随着迭代次数的增加，持续读写 IPDOM 硬件块会产生额外的流水级开销与读写功耗。
2. **基于谓词掩码修改的 `pred-tmc` 机制**：该方案实现了**完全无栈化（Stackless）**的循环控制流。底层硬件将 `pred` 指令映射至状态控制单元，通过就地过滤覆写线程掩码寄存器（TMC CSR）达成流控。在评估迭代判定时，不再满足条件的少数线程由于 TMC 位的阻断陷入“失活”（Inactive）从而被屏蔽；而只要宏观掩码探测器显示活跃数量大于零，调度系统便会将该 Warp 不断压后并重定向回头部进行下世代演算。待到全局线程均跳出循环阻断生效后，下文顺接一次原生 `tmc` 指令写回预存的最初掩码 `orig_tmask`，完成分支彻底收敛。该方法巧妙规避了传统栈机制溢出和栈存取开销的风险，对体量短促、不附带内层散状嵌套结构的标量化算法而言，具备显著的时钟级运行优势。

## 3 流式多处理器设计

### 3.1 整体微架构

本节从系统层面对所设计的 SM-Core 进行总体说明。在既定约束条件下，处理器仅支持 RV32IM 指令集与第二章定义的自定义扩展指令；不启用浮点扩展、不启用缓存层次与本地存储。该配置使得微架构设计重点集中在 SIMT 线程束调度、分支发散控制与多发射流水线组织上。

图 3-1 给出了 Core 级微架构总览。整体采用六级流水实现：线程束调度级（Schedule）、取值级（Fetch）、译码级（Decode）、发射级（Issue）、执行级（Execute）与提交级（Commit）。其中，前端以线程束为调度单位共享取指与译码通路，后端在执行与写回阶段按线程掩码控制各 Lane 的有效行为，从而实现“统一取指、并行执行、按掩码提交”的 SIMT 工作方式。

#### 3.1.2 对外接口与模块边界

从模块边界看，Core 对上接收启动与控制信息，对下通过标准化内存请求/响应接口与系统互连交互。由于缓存与本地存储被关闭，访存路径在本章中可抽象为“LSU -> 内存接口”的单级交互模型，这使得流水线行为分析能够聚焦于线程束状态演化、相关性阻塞传播与执行单元吞吐能力。

Core 内部各级之间通过统一的接口封装进行连接，接口中携带指令执行所需的核心字段，包括 `wid`、`tmask`、`PC`、`rd/rs`、`op_type`、`op_args`、`wb`、`eop/sop` 等。该设计方式将“数据路径字段”与“握手控制信号”解耦，便于在不同流水级之间插入可配置缓冲并维持时序稳定。

#### 3.1.3 六级流水线数据流概述

六级流水线可概括为以下主数据流：

1. Schedule 选择就绪线程束并给出当前 `PC` 与 `tmask`。
2. Fetch 根据 `PC` 读取指令，输出指令字与线程束上下文。
3. Decode 完成指令译码，生成执行类型、源/目的寄存器信息与扩展操作参数。
4. Issue 进行冒险检查与发射仲裁，将可执行指令分派至对应执行单元。
5. Execute 在 ALU/SFU/LSU 中执行，产生写回数据与控制反馈。
6. Commit 完成状态提交，回写寄存器并更新线程束控制状态（如分支发散、屏障、掩码更新）。

在控制流层面，后级会向前级反向传播阻塞信号，形成完整的 Backpressure 链路；在数据流层面，写回路径与调度状态更新路径在提交级汇合，保证线程束可见状态与寄存器可见状态的一致性。

#### 3.1.4 Interface 与 Elastic Buffer 机制

代码实现中大量采用 `interface + struct` 的方式组织跨级信号，其核心收益有三点：

1. 统一字段语义，避免跨模块手工连线导致的语义漂移。
2. 便于参数化扩展，在调整 `NUM_WARPS`、`ISSUE_WIDTH` 等参数时保持接口稳定。
3. 支持按需插入弹性缓冲（Elastic Buffer），在不改变功能语义的前提下优化时序收敛。

Elastic Buffer 采用 `valid/ready` 握手机制实现级间解耦：当前级仅在 `ready` 有效时推进数据，下级在拥塞时可回压上游。该机制一方面降低了长组合路径风险，另一方面为双发射场景下的突发阻塞提供了必要的时序裕量。后续第 3.6 节将结合控制流图进一步分析其反压传播路径。

综上，3.1 节建立了本章分析所需的统一抽象：以参数化六级流水为骨架，以线程束上下文为主线，以接口握手与弹性缓冲为时序保障。在此基础上，后续各节将按流水级分别展开调度、取值译码、发射与执行机制。

### 3.2 线程束调度级

线程束调度级是 SM-Core 前端控制的核心枢纽，负责在每个周期从“活跃且可运行”的线程束集合中选出下一条可发射指令对应的 `wid/PC/tmask`，并维护线程束生命周期状态。图 3-2 建议给出该级完整结构，包括线程束状态寄存器组、分支/屏障更新通路、IPDOM 协同单元与调度输出缓冲。

从功能边界看，调度级承担三类职责：

1. 线程束状态维护：维护每个线程束的活跃位、阻塞位、当前 PC 以及线程掩码。
2. 控制事件吸收：吸收来自执行与提交路径的分支结果、线程控制指令与同步屏障事件，并回写状态。
3. 下一线程束选择：在可运行集合内完成仲裁，向后级输出下一条取值请求。

#### 3.2.1 线程束状态寄存器组与维护机制

调度级内部以线程束为粒度维护四组关键状态：

1. `active_warps`：标记线程束是否处于激活状态。
2. `stalled_warps`：标记线程束当前是否被阻塞。
3. `thread_masks`：记录各线程束当前有效线程掩码。
4. `warp_pcs`：记录各线程束下一条待取指 PC。

这四组状态共同决定一个线程束是否可被调度。可运行集合可抽象为 `ready_warps = active_warps & ~stalled_warps`。当线程束被选中并成功发往后级后，调度级会先将其置为阻塞，等待译码/执行/提交侧事件返回后再解锁，从而防止同一线程束在尚未完成前一条指令状态更新前被重复调度。

在线程控制指令方面，`tmc` 会直接重写目标线程束的 `thread_masks` 与活跃状态；`wspawn` 在满足激活条件时批量置位多个线程束并初始化其 `PC` 与掩码；分支相关 `split/join` 则通过修改 `thread_masks` 与 `PC` 驱动发散与收敛。由此可见，调度级既是“选指单元”，也是“线程束状态机”的核心承载位置。

#### 3.2.2 屏障状态与同步控制

针对线程束级同步需求，调度级维护屏障相关状态寄存器组（barrier mask、计数器与阻塞位），用于记录每个屏障 ID 下已到达线程束集合与到达数量。当某线程束执行 `bar` 指令后：

1. 若该屏障条件尚未满足，则该线程束进入阻塞集合；
2. 若满足屏障触发条件，则一次性释放该屏障下等待线程束。

在本文采用的单 Core、无额外全局互联扩展分析范围内，可将其抽象为“局部屏障计数达标后统一解锁”的机制。该设计保证了线程束间同步的确定性，同时避免在执行级引入额外复杂同步控制逻辑。

#### 3.2.3 IPDOM 协同与分支发散支持

调度级通过 `split_join` 协同单元与 IPDOM 栈交互，完成 if-else 类型控制流的硬件化管理。其核心过程可概括为：

1. `split` 触发分化时，保存延后路径的 `PC + tmask` 上下文；
2. 当前优先路径继续执行；
3. `join` 到达后，按栈语义恢复待执行路径或汇合上下文。

IPDOM 机制使得线程束无需软件保存复杂分支上下文即可完成路径重放与汇合。需要说明的是，本节仅描述调度级如何“使用”该机制；IPDOM 存储结构、双槽位弹栈语义与时序细节将在后续章节结合专门图表进一步展开。

#### 3.2.4 与各级的关键数据交互

调度级与上下游关键交互可归纳为四条路径：

1. 向 Fetch 输出：`schedule_if` 输出 `wid/PC/tmask/uuid`，作为后续取值入口。
2. 接收 Decode 反馈：当指令不需要长期等待时，译码侧可回传解锁信号，释放线程束阻塞。
3. 接收 Execute/Commit 控制反馈：包括分支结果、线程控制指令提交结果、屏障到达信息等。
4. 向 CSR/状态侧导出：输出活跃线程束集合、线程掩码快照等运行状态。

从时序组织上看，调度级输出端使用弹性缓冲完成与取值级的解耦，使“线程束选择逻辑”与“下级是否可接收”分离。在后级拥塞时，调度级通过 `valid/ready` 握手自然回压，保证状态更新与发射行为的一致性。

综上，线程束调度级在本设计中并非传统意义上的单一仲裁器，而是融合了线程束状态机、同步控制与分支上下文管理的前端控制中心。其设计质量直接决定了流水线吞吐稳定性与控制流正确性，也是后续发射级与执行级性能表现的前提。

### 3.3 取值与译码

取值与译码位于流水线前端，直接决定后续发射级的输入质量与节拍稳定性。本设计中二者采用“取值请求-响应解耦 + 组合译码”的结构：Fetch 负责把线程束上下文与指令字正确配对，Decode 负责在单周期内完成指令类型判定与操作参数生成。图 3-3 建议给出该级结构图，突出请求标记回填、译码反馈解锁与前后级握手关系。

#### 3.3.1 取值级结构与关键机制

取值级输入为调度级输出的 `wid/PC/tmask/uuid`，输出为对应线程束的指令字及其执行上下文。由于指令存储接口存在请求与响应分离，Fetch 通过“标签映射存储 + 总线标记”机制保持上下文一致性：

1. 请求发出时，以 `wid` 为索引将 `PC + tmask` 写入本地 `tag_store`；
2. 响应返回时，从响应 tag 中恢复 `wid`，再从 `tag_store` 读回对应 `PC + tmask`；
3. 将恢复后的上下文与返回指令字拼接后送往译码级。

该机制保证了即使请求与响应在时间上解耦，指令仍能与原线程束上下文严格对应。结合本文“无 Cache/LMEM”配置，取值路径可简化为调度级到内存接口的直接指令读取链路，便于分析前端吞吐与回压行为。

此外，取值请求端采用弹性缓冲（`VX_elastic_buffer`）切断前后级时序耦合。请求通路在后级暂不可接收时可自动蓄压，避免将总线 ready 的组合路径直接反向传播到调度仲裁路径。对于无 L1 配置，Fetch 还维护了按线程束统计的在飞请求计数，用于避免前端持续注入导致下游缓冲耗尽。

#### 3.3.2 译码级结构与组合逻辑特征

译码级接收取值输出后，核心逻辑以组合电路方式完成以下任务：

1. 基于 opcode/funct 字段判定执行类型（ALU/LSU/SFU）；
2. 生成 `op_type` 与统一操作参数 `op_args`；
3. 提取 `rd/rs1/rs2/rs3` 与写回使能 `wb`；
4. 识别需要阻塞线程束的控制类指令并产生 `is_wstall` 标志。

在本文目标配置（RV32IM + 自定义扩展）下，译码主要覆盖整数算术、访存、分支与自定义线程控制指令。该级不引入复杂顺序状态机，功能上属于“输入到输出的一拍组合映射”，有利于保持前端低延迟。

译码结果通过 `decode_if` 输出至发射级；同时译码级还通过 `decode_sched_if` 向调度级回传“线程束是否可解锁”信息。若指令不属于需要等待后续控制结果的类型，调度级可提前释放该线程束，提升前端可调度集合规模。

#### 3.3.3 时序与延迟特性

取值与译码路径的时序特征可归纳为三点：

1. Fetch 请求侧采用带输出寄存的弹性缓冲，前向引入固定级间延迟，但显著改善了总线握手路径的时序闭合。
2. Decode 采用组合译码，并通过轻量缓冲将译码结果送往下级；在无额外流水寄存切分配置下，可视为“单级组合 + 握手转发”。
3. 前端整体通过 `valid/ready` 协议实现自然回压：当发射级拥塞时，回压会沿 Decode -> Fetch -> Schedule 逐级上传，保证指令与上下文不乱序、不丢失。

因此，3.3 节对应的前端设计在结构上体现为“功能组合化、时序解耦化”。它一方面通过组合译码降低控制路径延迟，另一方面通过弹性缓冲与握手机制抑制跨级长组合路径，为双发射后端提供稳定、可持续的指令输入。

### 3.4 发射级

发射级位于前端译码与后端执行之间，承担“指令整形、相关性约束、操作数就绪判定与执行单元分发”的桥接职责。对于本文配置 `ISSUE_WIDTH=2`，发射级采用双发射切片并行结构：译码输出先按线程束编号拆分到两个 issue slice，再由各 slice 独立完成缓冲、检查与分发。图 3-4 建议体现“上游单入口、下游多执行单元出口”的拓扑，以及每个 slice 内部的四级子路径。

#### 3.4.1 双发射组织与指令映射

顶层发射模块（`VX_issue`）通过线程束编号到发射域编号的映射函数，将来自 `decode_if` 的指令分配到目标 slice。该机制可以抽象为“按 `wid` 划分子域”：

1. `decode` 阶段保持单入口；
2. `issue` 阶段按 `wid -> isw/wis` 映射分流；
3. 两个 issue slice 并行运行；
4. 各 slice 输出再按执行单元类型重排到统一 `dispatch_if` 阵列。

这种组织方式与 `NUM_WARPS=16, ISSUE_WIDTH=2` 参数天然匹配，能够在保证线程束局部性（同一线程束长期落在同一 slice）的同时提高总体吞吐能力，并降低单个 slice 内部仲裁规模。

#### 3.4.2 发射级内部组件与功能分工

每个 issue slice 由 `ibuffer -> scoreboard -> operands -> dispatch` 四个子模块串接构成：

1. `ibuffer`：按线程束缓存译码指令，吸收前端突发流量，避免下游暂时拥塞时直接阻塞译码。
2. `scoreboard`：执行相关性检查与就绪判定，决定指令是否可继续向下游推进。
3. `operands`：完成源操作数供给与必要的写回旁路协同。
4. `dispatch`：依据执行类型将指令路由到 ALU/LSU/SFU 对应通道。

在本章中，这四者的关系只从系统级说明其“级间职责”；其内部硬件结构、冲突处理策略和关键时序细节将在第 4 章分别展开（其中 `scoreboard` 与 `operands` 是重点）。

#### 3.4.3 与写回及执行级的接口关系

发射级一端接收译码输出，另一端直接感知写回信息并向执行级派发：

1. 写回接口 `writeback_if` 回传目的寄存器与数据，用于发射级内部就绪状态更新和操作数前递判断。
2. 分发接口 `dispatch_if` 按执行单元类型导出 `op_type/op_args/rd/tmask/rs*_data` 等字段。
3. 发射级 `ready` 由下游反馈决定，当目标执行通道不可接收时，回压经发射级逐级上传至译码与取值前端。

因此，发射级在结构上同时承担“向后发射”与“向前回压”的双向控制角色，是流水线吞吐稳定性的关键节点。

#### 3.4.4 时序特性与延迟分析

在时序实现上，发射级主要通过弹性缓冲实现局部解耦：

1. `ibuffer` 采用可配置深度缓冲，吸收译码输出抖动并提供每线程束独立队列。
2. `dispatch` 端采用带寄存输出的弹性缓冲，将执行单元 ready 路径与上游组合路径隔离。
3. 各子模块之间统一采用 `valid/ready` 协议，形成天然的级间流控。

从周期行为看，发射级并非固定单拍组合路径，而是“由多级握手链构成的弹性流水”。在无阻塞情况下，指令可连续推进；在任一子模块或目标执行单元出现拥塞时，阻塞会沿 `dispatch -> operands -> scoreboard -> ibuffer` 方向反传，并进一步影响 `decode_if.ready`。该机制使双发射结构在高负载下仍能保持功能正确与时序可收敛。

综上，发射级通过“按线程束切片并行 + 子模块流水化 + 统一握手回压”实现了可扩展的双发射前后端耦合框架。该框架既保证了系统级吞吐能力，也为第 4 章的关键模块深度优化提供了清晰边界。

### 3.5 执行级

发射级完成指令分发后，指令流将路由至相应的执行单元执行。执行级（Execute Stage）旨在完成具体的算术、存储及控制流状态更新。根据前述配置边界（取消了浮点单元设计），本设计的执行级由三种核心执行模块并行组成：常规算术逻辑单元（ALU Unit）、访存单元（LSU Unit）以及特殊功能单元（SFU Unit）。

#### 3.5.1 执行级总体架构与并行接口

由于配置了双发射管道（`ISSUE_WIDTH=2`），执行级的顶层模块（`VX_execute`）采用对称通道阵列的拓扑结构。译码与发射级解析出的指令类型被硬连线映射至特定的执行流水线中：
1. **统一的输入输出封装**：所有的后端功能单元均对外暴露标准化的分发接收接口（`dispatch_if`）与执行写回提交接口（`commit_if`）。
2. **多延迟周期的弹性对齐**：由于不同类型单元（如单周期整数加法、多周期迭代除法以及不定周期的访存）的执行反馈延迟差异极大，这要求每个功能单元的出口位置必须配备带握手协议（`valid/ready`）的请求缓冲区（Re-order buffer 或弹性的 FIFOs），来保证在多指令并发执行时，不会因时序挤压而丢失写回结果。

#### 3.5.2 算术逻辑单元 (ALU Unit)

算术逻辑单元（`VX_alu_unit`）主要负责执行所有 RISC-V `I` 扩展的基础整数运算、`M` 扩展的乘除法以及分支判定。内部根据位宽与功能划分为两个具体的子执行管线：
1. **基础整数与分支处理 (`VX_alu_int`)**：负责单周期的加减法运算、逻辑位运算及移位操作等。同时，它也是条件分支指令（Branch）与跳转指令（Jump）的实体计算者。对于 `branch` 指令，算术逻辑模块验证比较条件，若发生跳转，将生成最新的目标程序计数器（Program Counter, PC），这些分支预测与判定信息将通过专用的旁路反馈接口（`branch_ctl_if`）在一个周期内上报给首端的调度单元，指导特定线程束重定向 PC 取指轨迹，从而缩小控制冒险惩罚。
2. **乘除管线 (`VX_alu_muldiv`)**：专门接收并完成 32 位的高延迟整型乘法与除法请求。为节省门级面积资源并兼顾性能，乘法器一般在模块内部被彻底流水线化，而除法则被实现为资源复用式的迭代状态机架构。

#### 3.5.3 访存操作单元 (LSU Unit)

与通用处理器不同，本章节设计的 GPGPU 核因为处于高度并行化且精简的高速运算流中，本版本特意剥离了所有本地共享片上内存（LMEM）以及多级数据缓存（Data Cache），因此，访存单元（`VX_lsu_unit`）成为了内核向更高速的外部内存通道存取数据的直接透传桥梁。
在 SIMT 并发模式下（`NUM_THREADS=4`），同一个 warp 的多条线程会各自生成独立的加载/存储地址。当前设计的 LSU 直接接收这组并行的地址请求序列，打包合成内存总线事物，通过主接口（`lsu_mem_if`）投递给芯片外的 Block RAM 总线。在其读取确认返回后，再由内部状态机拆解合并并将所检索到的有效数据经由 `commit_if` 返回寄存器堆，实现极简、无缓存的暴力存取模式，并依靠线程束的高度并发掩盖访存延迟。

#### 3.5.4 特殊功能单元与控制发散 (SFU Unit)

由于本设计引入了支持图形数据结构并发运行的自定义指令集扩展（包括 `split`, `join`, `wspawn`, `tmc`, `bar` 等操作），此类指令涉及整个微架构的状态转换计算，超出了常规 ALU 和 LSU 的界限，因此设计了特殊功能单元（`VX_sfu_unit`）将其囊括。该单元主要下设两大子模块：
*   **控制状态模块 (`VX_csr_unit`)**：提供标准的 `csr` 系列指令读写支持。它串联系统底层的各类运行状态监测传感器，包括指令执行计数、周期时间计数器以及硬件线程组（warp 和 core）的配置编号信息查询。
*   **线程束控制计算模块 (`VX_wctl_unit`)**：该模块是直接体现基于“硬件堆栈式分歧控制”功能的决策中枢。当发射端送入类似 `split`（分支产生）或者 `join`（分支聚合）这类非标准执行流指令时，由该模块解析源操作数中的掩码字。计算得到子线程的活动掩码与同步标识后，`VX_wctl_unit` 将打包生成一组线程束控制信号（`warp_ctl_if`）。该类控制信号被传递回顶层的调度级与独立的发散栈（IPDOM Stack）中，强制覆写当前的执行掩码状态并建立分歧断点，成为了第三章前述 IPDOM 栈硬件功能的唯一前端数据源动力。

通过 ALU 用于基础数学标量运算、LSU 专注于透传吞吐以及核心的 SFU 处理并行的流程发散，共同构建了一个边界清晰且极具可扩展性的完整执行域流水线。





### 3.6 控制流

与传统单线程超标量 CPU 追求单条指令极速乱序执行不同，本设计的 GPGPU 核心在流水线控制流管理上放弃了极其消耗面积且容易产生惩罚回退的“复杂分支预测与投机执行引擎”。系统全面贯彻了“无投机刷新（Flushless）、指令按需挂起（Stall）、全局后向反压（Backpressure）”的设计哲学，借助庞大的线程束并发度来隐瞒控制灾难与长周期延迟。

建议在此处绘制一张“Warp 状态转移与控制流反压传导路径图（Warp State Flow & Backpressure Diagram）”，集中反映下面两项核内动态机制。

#### 3.6.1 线程束状态机与分支处理策略

在调度前端（`VX_schedule`），每个硬件线程束（Warp）均维护了极其严密的状态边界，其完整生命周期中包含三个核心状态与转换流：

1. **休眠态 (Inactive)**：标识不参与本轮计算的资源池，由 `active_warps` 位图追踪。在硬件全局复位后，默认仅激活首个线程束（WID=0）。只有通过执行特殊的线程繁衍指令（如 `wspawn`）才会唤醒目标 Warp，或者通过掩码置零退出指令（`tmc`）使其重归休眠。
2. **活跃且就绪 (Active & Ready)**：该状态表示对应 Warp 可以参与竞争流水线资源（逻辑定义为 `active_warps & ~stalled_warps`）。调度仲裁器（Arbiter）将通过轮询机制直接从就绪池中提取指令并发往下游。
3. **指令挂起等待态 (Stalled)**：这是系统处理指令级控制冒险的核心手段。其包含两种截然不同的子行为：
   *   **防数据冲突的瞬时挂起**：任意 Warp 只要被调度选中向下投递，在当拍（`schedule_fire`）即被强制置位为挂起不可用状态（`stalled_warps_n[wid] = 1`）。这有效防止了该 Warp 在下周期产生紧邻指令发送，从而在 Fetch/Decode 前端结构中发生未知的数据依赖覆盖。
   *   **控制类指令的强制留置**：这是取代 Flush 的关键逻辑。指令一旦流至译码级（`VX_decode`）被识别解析，硬件会立即生成一个反馈信号 `is_wstall` 送回调度器。若判定该指令为基础算数、逻辑运算等常规组合，该信号为假，从而在译码拍立刻向调度发送解锁信号，令该 Warp 重新就绪以继续派发后续指令（此时下游记分板将处理它的 RAW 数据依赖）。
   *   反之，当译码检测到是一条 **改变控制流（分支 `branch/jal/jalr`）** 或是 **引起发散与屏障同步（`split`, `join`, `barrier`）** 的高危指令时，`is_wstall` 将置真，该 Warp 维持静默挂起。流水线内决不投机读取下一条后续代码，直到执行级（Execute Stage）将运算出确切的 PC 重定向或掩码条件结果（例如 `branch_ctl_if` 分支反馈网络）拉回，才会将该 Warp 真正释放继续工作。
   这一机制完全规避了传统 CPU 大面积的分支错误后 `Flush` 全管线的极高能耗与复杂撤销逻辑。

#### 3.6.2 全局弹性反压传导路径

为了确保各级流水线不因子功能单元的长短操作周期差异而破裂，系统摒弃了死板的全局流水寄存锁定锁，并在各交互层启用了全封闭的 `Valid/Ready` 非阻塞握手背压路径：
1. **阻塞源头与引发点**：通常发生于执行级内（例如 LSU 因无 Cache 请求系统总线的极长延迟，或 ALU 在处理不可流水化的整除法时被占用），此刻该单元的出口调度 `Ready` 拉低并回推。
2. **弹性缓冲吸收**：由于发射级（`VX_issue`）被切割成了多个子域并配置了发射缓冲区（`VX_ibuffer`）以及带输出寄存器打拍器的分发队列（`VX_dispatch_unit`），执行级的阻塞不会瞬间导致整机僵死。这些具有弹性的内部队列会逐层将等待中的译码请求吸收至内部 FIFO 耗尽。
3. **链路逆穿透**：当且仅当该具体 Issue slice 中的 `ibuffer` 因积压达到阈值上限，其自身的 `ready` 下拉信号才会沿级间的组合传输线，逆向阻塞译码级的派送（`decode_if`），接着抑制取指请求（`fetch_if`），并上报至调度器产生 `schedule_stall` 闭锁。

在这条反压链的传导过程中，若某一执行单元阻塞（如等待 LSU），受它影响的对应 Warp 切片将被局限于自己的缓冲列中；而完全不受此资源争抢影响且就绪的其他 Warp，将无缝切入流水线调度，由调度池自动填补执行单元出现的性能空隙。这一控制流架构极其精妙地掩盖了总线延时与运算气泡。

### 3.7 本章小结

本章自顶向下详细剖析了目标多核 GPGPU 微处理架构在 `SIMT` 模型下的整体宏观结构组织方式，围绕系统级设计的主数据流线进行了解构分析。

我们首先明确了系统基本配置规格（剥离复杂多级缓存、双发射切割部署、不支持乱序投机的顺序取指与发射环境），随之划定了从取指、译码、再到交由记分板（Scoreboard）处理指令窗口依赖和分发，最后向底层功能单元（ALU/LSU/SFU 等）导出的总时序接口行为与主要模块间的交握功能。我们并特别剖析了整个流水结构的控制流特色——通过精密的 Warp 挂起状态机及级间弹性反压，设计了一个免去误预测开销、抗干扰力极强的强吞吐框架。

第三章的内容明晰了该处理核中各“部件边界”和“流水运行机制”。而在这样的系统框架之中，诸如乱序如何防写后写冒险、寄存器争用如何通过特殊拓扑结构规避等模块级深层内部问题，将作为后续优化的核心所在，并在接下来的第四章《关键子模块设计》中予以更为详尽的技术性微观拆解。

## 4 关键子模块设计

### 4.1 计分板 (Scoreboard) 模块设计

在现代超标量处理器中，指令的并发执行非常容易触发数据相关性冲突（如 RAW 写后读、WAW 写后写等数据冒险）。GPGPU 虽然在系统级采用顺序发射体制，但为了掩盖不同功能单元（如 ALU 的单周期与 LSU/乘除法的多周期长延迟）因执行时间不对等而导致的延迟乱序写回，微架构中必须设计一套细粒度的挂起与解锁机制。本设计通过专用计分板（`VX_scoreboard`）模块接管并消解这些冒险。

#### 4.1.1 前向切割与并行相关性检查

为打破级联耦合引发的组合逻辑过长问题，计分板前端配置了带有物理寄存打拍的前向切割缓冲（Skid Buffer, 即 `staging_if`）。该结构不仅将前端 I-Buffer 与内部查表运算进行时序上的隔离，而且在背压发生时能有效掩盖控制环路带来的组合逻辑闭环（Combinational Loop）。

由于架构采用多线程束交织调度（`NUM_WARPS=16`，由每半区的 `PER_ISSUE_WARPS=8` 所映射），如果不加以剥离，全局查表将异常庞大且极易产生严重瓶颈。因此，计分板在内部建立了一张**分布式的状态追踪表**：为每一个微架构线程束分配了完全独立且平行的 32 位位图寄存器（`inuse_regs[31:0]`）。
*   当对应线程束的译码指令从发缓冲落入计分板的等待检查区时，硬件立即读取指令侧操作数地址（源寄存器 `rs1`, `rs2`, `rs3` 及目的寄存器 `rd`）。
*   随后立即向当前线程束专有的 `inuse_regs` 位图查询以上这 4 个寄器当前是否已被更早发出的、仍未写回的指令所占用。
*   一旦探测到任一关键操作数标志位为 1（忙碌），计分板内部将置低 `operands_ready`，此时调度级针对此特定线程束的后续操作将自然被阻塞，但完全不会影响其他线程束位图中尚未冲突指令的正向派发。

#### 4.1.2 旁路直通逻辑与写回清除

为了极力压缩“等待写回 -> 标志位释放 -> 指令重新尝试触发”带来的额外性能冒泡，该计分板利用快速直通机制深度优化了状态更新时序。
当长周期模块执行完毕、通过写入后总线（`writeback_if`）上报其最终结果（如 `rd` 地址及其 `wis` 归属）的瞬间，计分板无需等待寄存器堆实质落盘（SRAM 的写入建立阶段），直接在同一时钟拍中：
1. 精准将目标线程束的 `inuse_regs[rd]` 拉回可用状态。
2. 同步与滞留在暂存区 (`stanging_buf`) 正在进行源操作数查询的阻塞指令进行旁路比对，若释放的此 `rd` 恰好是阻塞所需的源数据之一或刚好解除了 WAW 锁，相应阻塞标志位（`operands_busy[i]`）马上在一拍内解套赋 0，从而实现指令的尽早发射解锁。

(*建议：微架构图在此部分应重绘体现 `inuse_regs` 的二维阵列结构，加上 `writeback_if` 对该结构的单拍清除转发线，以及它对 Skid Buffer 挂起与释放控制的具体握手路径*)。

### 4.2 寄存器堆 (GPR) 的 Bank 化映射设计

图形与并行处理核最显著的区别在于庞大且宽泛的数据吞吐度。在传统标量 CPU 中，一个 `3R1W`（三读一写）或者 `2R1W` 的数据接口即可应对单条指令的所有需求；但若是直接映射到含有 32 线程通道（`NUM_THREADS=32`）架构的 GPGPU 模型上，如果还采取传统的寄存器物理分离设计，等同于每一个时钟周期都有可能要请求 $32 \times 3$ 即近百个高速物理读操作端口。在实际 ASIC 设计及以块级内存（BRAM）为主要资源的 FPGA 设备上是不可能完成的物理铺设。为了克服此存储墙，设计采取了多体交织（Bank Interleaved）加向量内联的方式展开深度改进。

#### 4.2.1 线程数据向量化内嵌

所有处于相同 Warp 编号内的多通道线程所对应的同编号逻辑寄存器（如第 2 号 Warp 中的全部 `r5` 寄存器实例），在物理 SRAM 层面被横向强行打包，构成了一个总宽度为 `32通道 × 32比特 = 1024 Bits` 的超长词条 (Super Word)。
通过这一设计，硬件的读取通道从基于“线程”解除了耦合，无论多少个线程通道需要同步响应这一汇编指令，“读出此 Warp 对应 `r5`” 这一动作被浓缩为了针对一组 1024-bit 一次性的极宽单口 SRAM 访问，彻底解决了线程宽度扩张所引起的读端口数量爆炸。

#### 4.2.2 寄存器编号的 Bank 级交织映射

这虽然化解了多线程扩张之痛，但每条指令固有的多个独立操作数实体（如 `rs1, rs2, rs3` 三源操作数）访问却仍然要求存储器具备原生的 3 读支持。这种复杂结构的高速 RAM 一样极度珍稀。本架构通过“物理分块与交织编址”以时间换空间成功绕开了此限制。
寄存器堆在内部被横置切割为 `NUM_BANKS=4` 个互相独立的较浅的 RAM 体，每个 Bank 仅支持最基础且最廉价的 $1$读$1$写 ($1\text{R}1\text{W}$) 物理接口。为了规避同时读取 `rs1, rs2` 时碰巧遭遇访问同一个 Bank（导致端口撞车锁死）的严重后果，寄存器根据其编号位元被散列分布：
*   **Bank 选择域 (`req_bank_idx`)**：由目标编号的最末两位 `reg[1:0]` 决定。这样带来的效果是 `r0` 被映射入 Bank0，`r1` 在 Bank1 ... `r4` 又回到 Bank0，在空间上形成紧密的轮转交发。基于编译器通常就近连续分配通用寄存器（如 `MADD r1, r2, r3`）的空间局部性统计特征，三路源请求击中互相异构的不同 Bank 的概率远大于碰撞概率。
*   **Bank 内寻址域 (`req_in_data`)**：将剥离上述两比特之后的更长编号位 `reg[4:2]`，强行与上文所属的线程束编号 `wis` 拼接组合 (`{reg[4:2], wis[1:0]}`)，进而构造出了该向量字块在物理 SRAM 芯片内部的深层存址。由此达成了多 Warp 同一编号寄存器在行维度向下的空间纵列排布。

### 4.3 操作数网络 (Operands) 结构与冲撞流水

上述的拆解为整个核心的源级寄存器阵列设计搭建了根基，但从发射端接收记分板发来的物理请求，至成功回吐所需读出的各源操作数值供后端利用，其间需要一段高效且富有弹性、能自主处理底层“碰撞冲突”的控制网络。`VX_operands` 模块被专门构筑为一个紧密互联的三级独立运算流水线。

1.  **阶段 0：寻址仲裁与撞车拦截 (`Req Arbiter & Collision Check`)**
    发射至操作数模块的有效指令立刻接受其 `src_regs` 的拆解。如果三路读请求恰巧避开了 Bank 互斥限制（如请求分别落在 Bank0, Bank1 与 Bank3），对应的 3 位多路选择掩码会被交叉互联器 `VX_stream_xbar` 一拍通过直塞。
    若极其不幸遭遇同一 Bank 的竞争碰撞（例如判定 `req_bank_idx[i] == req_bank_idx[j]` 成立），系统在此周期马上拉低当前发射级接受的准入信号 (`has_collision_n = 0`) 反压记分板的派送进度；在内部工作上，被阻塞的数据项会被滞留或回压寄存打拍（`pipe_reg1`），这也就意味着，本该在一个节拍完成的大字面宽读操作现已被自动分裂并被串行化为两个及以上的工作流水状态来隐蔽拉平冲突带来的数据获取时间差。
2.  **阶段 1：物理阵列读取 (`SRAM Read & Write`)**
    第一站输出的无安全冲突地址（`gpr_rd_addr`），以对立并行的物理口同时推入各个 Bank (`gpr_ram`)。经过标准确定的 1 周期静态获取时延，所有成功被锚定的 `1024 Bits` 超长向量返回至暂存寄存级 `pipe_reg2` 对端接口之上。与之相向配合的，写回操作 (`wbuf`) 往往在同一时延窗口不抢占当前正读物理块资源的安全口中完成无缝写回落库。
3.  **阶段 2：重组与对外投发 (`Data Assemble & Output Buffer`)**
    既然指令的 `rs1` 并非定死对应于 0 号 Bank，后端吐出的横向原始数据也必定是一组乱序队列。阶段二逻辑以打拍沿留的源路记号作为指针将散落出来的四道输出再次映射聚集，将属于 `rs1` / `rs2` / `rs3` 原位的值从被击中的相应存储槽原路拉出。
    这一组重组且合体后的庞大位宽向量群最终连贯挤入专设的尾部弹力收缩 FIFO (`out_buf`) 之中，作为后处理算数的子弹库向派发网络 (`VX_dispatch_unit`) 以确定的 `operands_if` 接口吐出。整条链路通过握手防拥手段与底层交织映射完成了极高速且纯并列的宽频存取，大幅规避并压缩了核心关键门级的结构开合延迟效应。

### 4.4 LSU访存单元与外联调度设计

在现代 GPGPU 设计中，由于取消了复杂的本地共享内存（LMEM_ENABLE=0）与重负荷的数据缓存（D-Cache）网络，加载/存储单元（`VX_lsu_unit`）成为了内核向不确定延迟的外部主推总线（如 L1 总线或系统内存）透传数据的直接枢纽。这也使得 LSU 必须依靠高度弹性的硬件结构来消化极端的长延迟与乱序回传。结合简化版的微架构设计，其核心逻辑落位于每个独立的 `VX_lsu_slice` 之中。

#### 4.4.1 基于双端分流的存取解耦流水线

面对寄存器写回机制的要求，存（Store）与取（Load）表现出了截然不同的生命周期：Store 不产生任何供同线程束计算的数据回调，只要指令送达请求缓冲口即可宣布执行结束；而 Load 却必须苦等外部数据线的回灌。为了不让 Store 枯等 Load 缓慢的仲裁延时而导致流水线拥塞，各切片内部设计了一条极富特色的异步“双端分流”物理通道结构。

经过前端组合逻辑的基址寻址计算与 Byteen 对齐整形后（纯组合逻辑，0 Delay）：
*   **瞬时抛弃旁路 (`no_rsp_buf`)**：所有单纯发往外部且不需要写回 GPR 的指令（如普通的 Store 请求），在地址落入此深度为 2 的高速 FIFO （引入 1 Cycle 缓冲）的同时，硬件直接组装出一个带原生 `WID` 且 `data=0`、`wb=0`（不写回）的伪答复包裹。这就如同发后即忘，将存操作直接导向合并级准备退役释放。
*   **长效等待主线 (`mem_sched`)**：需要拉取数据的 Load 正常推进到外部物理队列调度器中被挂起。
在这两条时间差异极大的分线末尾，配备了以 Load 优先的读写管线交汇仲裁器（`rsp_arb`）。通过分流策略，那些本不需要等待反馈的数据通路不会受到长周边设备延宕拉扯带来的同向背压阻塞，最大化清空前端资源。

#### 4.4.2 无缓存环境下的标签寄存与乱序回溯

系统透传外联时面临的核心挑战是：外部块 RAM 或总线响应乱序不可控且只能承载极短的系统身份请求。为了保证传回的数据重新归位给上层数百个并发排队的线程且送进确切的 `rd` 寄存器目标，底层的访存调度器（`VX_mem_scheduler`）引入了基于分离式字典的标签重溯模块（`VX_index_buffer`）：

*   当 Load 请求离港打入总线时，调度器将其涉及整个微架构身份的庞大元数据实体（包含 `rd`/`pc`/`tmask`/`wid` 等数十位宽请求标签：`core_req_tag`）剥离并在本地物理 RAM 表（`req_ibuf`）中以新的精简游标地址（`ibuf_waddr` 写入槽位）建档寄存。
*   只有这个极短的轻量化地址游标会被带上外部时钟周期的总线漂流。
*   漫长等待后，无论数据如何乱序沿 `mem_rsp` 返回端反馈，调度器立刻拾取该标签并检索本地字典（`req_ibuf` 的读取端 `ibuf_raddr`），一拍之内即可把这个孤立的字节唤醒还原成具备完整身份的回传提交包裹。这一隔离型代理机制有效削减了往返总线必须随载的昂贵位宽开销。

#### 4.4.3 显式屏障阻塞控制机制 (Fence Lock FSM)

GPGPU 极度密集的并行读写环境极其容易因地址冲撞引发一致性风险。本设计虽然不采用复杂的 Cache 一致性网络，但在 LSU 硬件执行面上加入了全局强硬的隔离锁存机制（Fence Lock FSM）。
当译码出一跳屏障访存围栏指令（`FENCE`），不仅前端停止派发，在到达 `VX_lsu_slice` 时：
1. 组合逻辑立刻判定 `req_is_fence` 为真。
2. 内部硬件状态机在当前指令被后端确据派发后的当拍，将其锁死置位 `fence_lock <= 1`。该常高电平将作为最核心的关卡，彻底屏蔽拉低其后的准入信号 `mem_req_valid`，形成刚性的硬物理截断。
3. 直至且仅当 LSU 发送队列（`no_rsp_buf`及`mem_sched`）中先前长达数十拍的所有的旧有 pending（未完成）发包全数落盘清零并且触发清空信号之后，该 `fence_lock` 方才缓慢落下并解锁当前阻塞域。这种无任何投机的物理阻断构筑了该数据模型多通道操作安全的托底保障。
